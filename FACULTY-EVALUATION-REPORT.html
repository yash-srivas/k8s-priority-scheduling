2. Industry Priority Governance (How Real Companies Determine Priorities)

In production (Google Borg, Netflix, Uber, AWS EKS), developers never pick priority scores arbitrarily. Priorities are governed by formal platform policies:

A. Service SLA Tiering Matrix
  • Tier-0 (P0 - Critical Path): Payment, Auth, Checkout APIs. Cannot tolerate pending latency. Priority: 100000+.
  • Tier-1 (P1 - Core Services): Catalog, Search, Inventory. User-facing but can queue briefly. Priority: 50000.
  • Tier-2/3 (P2/P3 - Batch): Video transcoding, ETL, ML training. Interruptible jobs. Priority: 10000.
B. Automated Policy Injection (Admission Webhooks)

Engineers are strictly prohibited from setting high-priority manually. Validating/Mutating Admission Controllers (OPA Gatekeeper / Kyverno) inspect CI/CD metadata and automatically inject the approved PriorityClass based on registered service catalog tiers.

3. kube-scheduler Mechanics: Priority Queue & Two-Phase Cycles

Kubernetes does not use FIFO queueing. Internally (within pkg/scheduler/internal/queue/scheduling_queue.go), kube-scheduler maintains an active queue (activeQ) structured as a Heap-Based Priority Queue:

Pod Submitted → API Server → activeQ (Max-Heap by Priority Value) → Pop Highest Priority Pod +----------------------------------------------------------------------------------------------------+ | 1. SCHEDULING CYCLE: [Filter Phase] (Node Capacity >= Requests?) → If NO → [Enter Preemption Cycle] | | [Score Phase] (Rank fitting nodes) → [Reserve/Permit] → [Bind to Node] | +----------------------------------------------------------------------------------------------------+ | 2. PREEMPTION CYCLE: a. Filter nodes where evicting lower-priority pods frees required CPU | | b. Select minimum victim count with lowest priority (evict low, keep medium) | | c. Set nominatedNodeName → Issue SIGTERM → Victims exit → Bind high-priority Pod | +----------------------------------------------------------------------------------------------------+
Scheduling Priority vs. Linux Kernel QoS:
• PriorityClass: Controls kube-scheduler placement & preemption when CPU/Memory Requests are saturated.
• QoS Class (Guaranteed/Burstable/BestEffort): Controls Linux oom_score_adj for the Linux Kernel OOM-Killer when physical host RAM runs out. Real Tier-0 services use both High PriorityClass and Guaranteed QoS.

4. Baseline Cluster State & Precise Mathematical Resource Proof

The Baseline represents the verified, saturated cluster utilization. Preemption cannot be proven on an empty node because preemption is strictly triggered when node resource capacity is exceeded.

Target Node Baseline Accounting (Node: kind-worker):
Total Allocatable CPU: 16,000m (16 cores). System Daemon Reserve: 100m.
Baseline Deployed Workloads: 1 × Medium Pod (1,590m) + 3 × Low Pods (3 × 3,975m = 11,925m).
Committed Requests = 100m (sys) + 1,590m (med) + 11,925m (3x low) = 13,615m Residual Free CPU Available for Scheduling = 16,000m - 13,615m = 2,385m

To prove priority governs scheduling, two identical workloads (4,373m CPU) were tested against this 2,385m residual headroom (Deficit = 1,988m):

Case A: Equal-Priority Probe (Low: 10,000)

Request: 4,373m • Deficit: 1,988m.
Evaluation: Existing node pods are Medium (50k) and Low (10k). Kubernetes rules strictly forbid preempting equal or higher priority pods.
Result: Remained Pending continuously. Logged FailedScheduling: Insufficient cpu. Zero victims terminated.

Case B: High-Priority Arrival (High: 100,000)

Request: 4,373m • Deficit: 1,988m.
Evaluation: High priority (100k) exceeds low pods (10k). Evicting one low pod frees 3,975m.
Post-Eviction Headroom: 2,385m + 3,975m = 6,360m ≥ 4,373m.
Result: Native Preempted event fired. Low pod terminated. High pod placed to Running. Medium pod preserved. Final Free CPU: 1,987m.

6. Faculty Defense / Viva Examination Q&A Cheat-Sheet

Q1: "Did you write custom scheduling algorithms or priority queues in Python/Flask?"
Answer: No. Flask is strictly an out-of-band monitoring dashboard and script runner. 100% of scheduling logic, heap sorting, node filtering, scoring, and preemption cycles are executed natively by the compiled Go binary kube-scheduler in the control-plane container.
Q2: "Why do your containers run sleep commands instead of real processing workloads?"
Answer: Kubernetes scheduling decisions are computed against Declared Resource Requests (spec.containers.resources.requests) admitted into etcd, NOT runtime CPU spikes. Using lightweight containers allows us to demonstrate massive enterprise multi-core resource scheduling cleanly on a laptop without thermal throttling.
Q3: "Why did the high-priority pod preempt a low-priority pod and NOT the medium-priority pod?"
Answer: The native kube-scheduler preemption algorithm implements victim minimization: it seeks to evict the lowest possible priority tier first, and the minimum number of pods necessary to satisfy the deficit. Evicting one low-priority pod (3,975m) satisfied the 1,988m deficit completely, leaving the higher-priority medium pod untouched.
Q4: "What happens if two pods have the exact same PriorityClass value?"
Answer: Within activeQ, if two pods share identical priority values, the scheduler breaks ties using creationTimestamp (FIFO ordering). If priority values differ, priority strictly supersedes creation time.
Live Cluster Verification Command: kubectl get events -n priority-scheduling --sort-by=.metadata.creationTimestamp
